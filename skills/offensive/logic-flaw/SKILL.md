# discovery.logic-flaw

domain: web  
tags: discovery, logic, idor, authz, race

Probe for business logic flaws — IDOR, privilege escalation, race conditions, and auth bypass.

## 何时使用

- `entity:web.endpoint`（信任级别 ≥ claim）
- `observation:web.endpoint`（信任级别 ≥ claim）

## 预期结论

- `hypothesis:logic.vulnerability`
- `observation:web.finding`

## 侦察与判定信号

- 先建立"对象—身份—动作"三角：每个接口操作谁的对象（ID 从哪来）、以什么身份（会话/角色/租户）、
  允许什么动作（读/写/审批/导出）。
- 越权信号：把 A 的身份与 B 的对象组合起来，服务端是否仍然按 A 的意图执行。
  横向（同角色不同用户）与纵向（低权限做高权限动作）分别记录。
- 流程信号：状态机里的顺序依赖（先验证再改邮箱、先支付再发货）、可跳步、可重放、可并发。
- 判定信号：逻辑漏洞的证据通常是"业务结果错了"，而不是"技术栈报错了"。

## payload 家族与变体

- 标识符交换：把自己的 ID 换成相邻/猜测/泄露的 ID（顺序、UUID、时间戳、自增）。
  变体包括参数位置（query/body/header）、批量接口、嵌套资源路径。
- 身份降级：去掉会话、换成低权限会话、伪造租户头（`X-Tenant`、`X-User-Id`、`X-Forwarded-For`）。
- 状态跳跃：跳过前置步骤直接调用后置接口；重复提交同一请求；并发提交（竞态）。
- 数量与边界：负数、零、极大值、重复键、字段缺省、类型混淆（字符串 vs 数字）。
- 变体原则：每次只改一个维度，保证能归因。

## 预期证据形态

- `hypothesis:logic.vulnerability`：写清被打破的不变式（例如"只有对象所有者能读"）。
- `observation:web.finding`：两次请求 + 两次响应的对照，展示结果差异。
- 竞态类证据要写清窗口条件与重复次数，并说明是否可能造成重复扣款/重复领券等副作用。

## 操作边界

- 不做批量枚举用户对象；用一两个可证明差异的样本即可。
- 禁止会破坏业务数据完整性的验证（真实下单、真实转账、群发通知）。
  遇到此类接口，用"是否可到达该状态"的只读证据替代。
- 竞态测试要限制并发数与重复次数，避免把目标拖入不一致状态。
- 涉及真实用户数据的响应只引用结构差异，不留明文。

## 常见坑

- 把 403 当成"不可越权"：换身份、换路径、换方法后结论经常反过来。
- 只测一个参数位置，漏掉同名参数在 body/header 中的处理差异。
- 在需要多身份的场景里只用一个会话，无法构成对照。
- 把自动化扫描器的逻辑模板命中当成结论：逻辑漏洞几乎都需要人工构造对照请求。
- 忽略业务语义：技术上"成功"的行为可能只是设计如此，判定要看题目目标与不变式。

## 提示

- 用授权范围内的最小化动作推进，不做破坏性利用或持久化。
- 结论写完后写入 ``；竞争会话可把摘要同步到 ``，不提交 typed World 事件。
- 关键发现与排除路径记到 `$HARNESS_NOTES_DIR` 下的 markdown 笔记。
