# report.submit

domain: report  
tags: report, submit, vrp

Format and submit vulnerability report to ZC platform with PoC evidence.

## 何时使用

- `observation:vuln.confirmed`（信任级别 ≥ claim）
- `artifact:vuln.poc`（信任级别 ≥ claim）

## 预期结论

- `observation:report.submitted`

## 侦察与判定信号

- 提交前的自检：这条结论是否已有可复现的最小证据？是否越过了授权范围？是否已经把
  "我很有把握"和"已验证"混为一谈。
- 去重检查：同一个候选只提交一次。被拒绝的候选是修正假设的证据，不是重发理由。
- 得分形态：多 Flag 题目每个得分点独立提交；同一入口的多个变体要判断是不是同一个得分点。
- 判定信号：可以提交的条件是"证据成立 + 属于本题目标 + 尚未提交过"。

## payload 家族与变体

- Flag 形态：`flag{...}`、题目自定义前缀、编码后的字符串。发现候选先按题目声明的格式校验，
  明显不符合格式的候选不要提交，避免浪费提交次数与噪声。
- 候选来源：响应正文、响应头、错误回显、文件内容、带外回调记录、平台题目描述中的提示。
- 变体：优先提交"直接观测到的值"，而不是从观测值推导出的变换结果（除非题目明确要求变换）。
- 报告形态：标题（漏洞类型 + 位置）、影响、最小复现、证据引用、修复建议。

## 预期证据形态

- `observation:report.submitted`：提交的候选类型与值（trace 侧只保留哈希）、提交结果与得分变化。
- 报告正文引用 `artifact:vuln.poc` 与 `observation:vuln.confirmed`，不复制大段响应体。
- 被拒绝的提交同样记录：候选、原因、以及据此修正了哪条假设。

## 操作边界

- 只提交属于本次授权目标与当前题目的候选；不提交其它题目、其它队伍的候选。
- 不在提交内容里包含凭据、个人信息或大段数据转储。
- 遵守平台限速与判分规则；提示（hint）类动作会扣分，只在收益明确时才用。
- 未验证的猜测不要提交，重复提交同一个值会被去重，也可能影响判分。

## 常见坑

- 把"应该能拿到 flag"当成已拿到，提交失败后继续重复提交同一候选。
- 只提交、不落库：提交结果不写回世界状态，导致后续无法解释分数来源。
- 报告写成过程叙述而不是最小复现，团队与平台都无法复核。
- 忘记区分"我确认了这个漏洞"和"平台确认了这个漏洞"。

## 提示

- 用授权范围内的最小化动作推进，不做破坏性利用或持久化。
- 结论写完后写入 ``；竞争会话可把摘要同步到 ``，不提交 typed World 事件。
- 关键发现与排除路径记到 `$HARNESS_NOTES_DIR` 下的 markdown 笔记。
